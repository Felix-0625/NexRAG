# 业务指标与查询结果的不同口径

NexRAG将注册业务指标与SQL结果行数分开传递。三条商品记录可以对应两个订单；返回三行不能自动解释成三个订单。模型选择获授权的指标，数据库计算数值，最终报告引用证据ID，后端显示指标、单位及明细。

## 指标目录

继续使用现有业务数据源的metadata文件。项目示例为`examples/olist/metadata.yaml`；通过界面连接的数据源使用本机`data/ops/business-profiles/<连接ID>/metadata.json`。目录由受信任的数据源维护者审阅维护，不由员工或Agent自行改写。数据库字段不能自动证明企业的业务口径，因此新连接不会凭字段名自动注册财务指标。

```yaml
metrics:
  order_count:
    table: orders
    calculation: COUNT(DISTINCT order_id)
    description: 订单数
    aliases: [成交笔数]
    kind: count
    unit: orders
  order_total:
    table: orders
    calculation: SUM(amount)
    description: 订单总金额
    kind: amount
    # 只有业务元数据明确币种时填写unit；缺省显示“未定义”。
```

`kind`为`count`、`amount`或`number`，默认`number`。计数必须使用COUNT/COUNT DISTINCT。公式只能是一个已声明业务视图上的聚合表达式；明细裸列、窗口、子查询、跨视图引用、多条语句均拒绝。SQLGlot负责解析和构造SQL，最终仍通过原有AST、只读连接及租户快照执行，不引入另一套数据库权限。

## 调用与输出

Agent通过`query_business_metrics`提交目录里的指标ID及明确的字段比较条件。多个视图的指标分别聚合、共用本轮快照，避免把订单金额复制到每个商品行再求和。每个过滤条件必须适用于该批全部指标，否则整批拒绝，不会静默删除条件。复杂探索继续使用原有`query_database`，其结果不冒充已注册企业指标。

结果使用Pydantic模型验证，包含`metric_id`、`value`、`kind`、`unit`、`view`、`grain`、`calculation`、`scope_id`、`snapshot_id`和`filters`。查询行数属于SQL结果元数据。SUM没有数值时保留null，不擅自改成零。

对请求中明确出现的目录指标ID、完整规范名称或维护者登记的`aliases`，执行前逐个绑定指标义务。例如“订单数、订单总金额和商品行数”对应三个独立的指标；取得商品行数不能替代订单数，也不能把已查出的金额当作未查询指标的值。用户明确要求关联明细且这些指标跨多个视图时，还必须取得相应视图的一次经过粒度认证的关联明细结果。单表明细不会因为返回了若干行而满足该关联要求。未完成时反馈具体缺少的指标ID与关联要求，且禁止完成报告。

这是基于企业目录的有界名称解析，避免为每个问题新增正则规则；不是任意自然语言语义的证明。目录别名仍需维护者审阅，未登记的改写、歧义名称及行业口径必须继续实测，不能因为这组契约回归通过就宣布复杂问答全面验收。


取得注册指标后，Agent使用PydanticAI的`complete_business_report`输出实际指标ID和明细/知识证据ID。这个结构没有供模型重写数值的字段，也不接受任意说明文本；后端按本轮实际结果生成表格。若本地模型仍以文本结束，证据齐全时后端直接收集本轮实际引用、执行相同报告校验并生成表格，忽略模型文本中的数字，不额外要求模型重新抄写证据ID。证据不齐仍要求补查或明确回退。不存在、类型不符或遗漏的证据引用会拒绝。知识结论来自原有授权检索，不因业务指标授权而扩大知识库范围。

未使用注册指标的普通对话、文件、知识和自由SQL路径保持兼容。现有文本数值检查作为这些路径的有限防护，不是通用业务真伪判定器。

## 验证边界

两个同为100的订单应合计200，不能用SUM DISTINCT金额得到100。订单2个与商品3行应作为两个指标分别展示。注册公式仍需维护者确认业务含义；类型校验、主键和SQL语法都不能证明企业定义正确。本实现不提供任意多对多指标自动重写、跨视图公式优化或完整数据仓库服务。

设计依据：[dbt实体与关联规则](https://docs.getdbt.com/docs/build/join-logic)、[Snowflake行级事实与聚合指标](https://docs.snowflake.com/en/user-guide/views-semantic/validation-rules)、[PydanticAI结构化输出](https://github.com/pydantic/pydantic-ai/blob/main/docs/output.md)。本项目复用SQLGlot、Pydantic/PydanticAI及数据库聚合，不依赖部署上述数据平台。

2026-11-01验收撤回基于自然语言过滤词黑名单的自动全量补查：未知地区或状态修饰可能被漏判，不能据此授权全量口径。保留目录逐项义务、真实授权指标工具和缺项拒绝；复杂原题仍未全面通过。

本轮修正明细完成条件：要求关联完整明细并查询跨视图注册指标时，同一份关联结果必须包含所请求非计数指标的实际输入列，例如`orders.amount`。通过SQLGlot解析直接投影及别名，常量或计算列不能冒充源列；选定报告引用再次检查，不能凭账本中其他完整结果放行残缺表格。校验不自动执行SQL、不改写列和过滤条件，也不保证识别任意未登记的自然语言字段。

无效指标ID和不通用的过滤字段返回当前已授权目录中的纠错信息；未授权时先拒绝，不返回目录。过滤条件不匹配时仍整批拒绝，不擅自改成全量查询。复用[PydanticAI输出验证与纠错](https://pydantic.dev/docs/ai/core-concepts/output/#output-validators)，不新增Agent或平台组件。

当注册指标报告的全部绑定义务（包括需要的明细列、知识、计算、导出）都已取得真实依据时，使用PydanticAI的`prepare_tools`进入报告阶段：隐藏采集工具，保留结构化报告与文本输出，再执行原有授权和输出校验。不是用超时回退冒充完成，也不依赖Ollama不保证执行的`tool_choice`。普通对话以及仍有缺项的请求继续使用原有工具循环。未登记的自然语言字段/过滤意图仍属于当前有界契约的限制，不能据此声称任意复杂问答通过。

空指标目录现在显式说明没有注册指标，并在当前轮隐藏`query_business_metrics`，避免模型虚构指标ID。普通授权只读查询仍可使用。已验证的折扣计算也复用结构化报告：金额、比例、优惠和折后金额分别由服务端从本轮工具结果渲染，不要求模型重写数值；没有真实计算证据时不能生成这类报告。

自由SQL的WHERE/HAVING直接比较、IN、BETWEEN字面量，以及模型传入的注册指标过滤值，执行前增加当前问题依据检查。用户未提到的`status='completed'`会被拒绝，不会悄悄删掉条件并执行全量查询。已核验的当前租户标识可以沿用，权限仍由租户快照和只读适配器独立执行。复杂表达式、相对日期转换、否定和比较运算符的自然语言等价性不由字面量匹配证明；有歧义应明确条件或维护目录映射，不能把这个有界检查称为通用SQL语义证明。

这里沿用[dbt语义层区分指标、维度与查询过滤](https://docs.getdbt.com/guides/sl-qs)的职责划分，没有引入dbt运行组件。目录内固定公式与模型额外提供的过滤值分开管理。

文档派生算术使用内部只读工具 `calculate_evidence_arithmetic`，复用标准库 Decimal 与固定算子。每个操作数必须指向本轮实际读取的证据、数值和原文摘录；不存在的摘录、未出现的数值、导出产物和零分母均拒绝。工具记录真实结果后仍经过原数字及指标口径检查，不能把任意计算结果重新命名为已核验的业务总额。它不执行代码、SQL、文件或网络操作，也不替代管理员授予的数据读取权限。算术正确与来源绑定不证明单位一致或业务公式正确，业务指标仍以已登记口径为准。

2026-11-02公开金融真实模型批测发现：数字确实存在并不证明其单位或指标正确。增加有界百分比来源校验：原文明确百分比可以引用，派生百分比须来自实际`percentage`或`percent_change`运算及其记录的舍入结果；`subtract`得到的货币差额不能直接添加`%`。格式指令中的“保留0位小数”不再授权事实值0。该检查不识别任意财务指标或年份语义，不能把错误指标的安全拒绝视为正确回答，也不能将执行状态`ok`当作答案质量达标。复用[PydanticAI输出验证及纠错](https://pydantic.dev/docs/ai/core-concepts/output/#output-validators)；计算与推理分工参照[Program of Thoughts](https://arxiv.org/abs/2211.12588)，没有引入任意代码执行。
